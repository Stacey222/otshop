# Thumbnail generation

Phase 3 Slice 3.3 generates exactly one preview derivative for an already inspected `READY` media asset. It does not re-inspect, transcode, normalize, publish, or modify the original video.

## Boundary and flow

`POST /api/media/<mediaAssetId>/thumbnail` requires same-origin authentication, the active workspace, and the existing `media.upload` permission. The route accepts only the media UUID. The application performs a workspace-qualified lookup and optimistic claim before it opens the trusted original through `StorageProvider`.

`MediaDerivativeGenerator` separates orchestration from native execution. `FFmpegThumbnailGenerator` uses a server-configured executable, `shell: false`, a fixed argument structure, stdin media, and stdout image data. It accepts no client path, URL, timestamp, dimensions, environment, or arguments. The default timeout is 15 seconds; JPEG stdout is bounded by `THUMBNAIL_MAX_BYTES` and stderr by `FFMPEG_MAX_DIAGNOSTIC_BYTES`. The child is terminated and awaited on timeout, overflow, input failure, or process failure.

## Deterministic policy

The representative timestamp is 10% of the inspected duration, capped at 10 seconds. FFmpeg selects the primary video stream and emits one JPEG using one codec thread and fixed quality/filter arguments. The scale filter preserves aspect ratio, does not upscale, and bounds both axes to `THUMBNAIL_MAX_DIMENSION` (640 by default). There are no size variants, contact sheets, AI selection, or derivative videos.

Successful process exit is insufficient. The application verifies non-empty bounded bytes, JPEG start/end markers, structurally bounded segments, a start-of-frame dimension record, a scan marker, positive dimensions, and the configured maximum dimension. No image-processing dependency is required.

## Storage, coordination, and compensation

The canonical opaque key is `thumbnails/workspace/<workspace-id>/media/<media-id>.jpg`; it contains neither the upload filename nor a client path. Generated bytes are written under a server-generated `temporary/` key and promoted with the local adapter's same-filesystem create-without-overwrite hard link. The final object is read-only and cannot replace an existing object.

`thumbnail_generation_started_at` is a nullable coordination lease, not a media status. A version-checked claim is available only for `READY` rows with no thumbnail. A fresh claim returns an in-progress conflict; a claim older than the conservative stale interval can be reclaimed after process failure or restart. Version-checked completion atomically writes the existing `thumbnail_key` field and clears the claim. A late claimant cannot overwrite newer state.

Repeated requests validate and return the persisted canonical object without running FFmpeg. If promotion succeeds but database commit cannot be confirmed, the immutable object is preserved rather than risk deleting referenced content. After the claim becomes stale, a later request validates that canonical orphan and persists it without rerunning FFmpeg. Failures before promotion delete the temporary object and release the exact claim when possible. Cleanup/release ambiguity is logged for reconciliation without exposing keys or paths.

## API and operational limits

The response contains media ID, availability, JPEG MIME type, byte size, encoded dimensions, and whether this request created the canonical object. It never contains a storage key, filesystem path, command line, stdout, or stderr. Logs contain only request/workspace/media IDs, outcome, duration, size, and dimensions.

Binary thumbnail serving is intentionally deferred; thumbnails are not written under `public/`. `READY` and thumbnail availability do not claim malware safety, Shopee compatibility, or publishing readiness. FFmpeg timeout and bounds reduce resource risk but are not an OS sandbox; native decoder vulnerabilities and privileged host mutation remain deployment concerns.
